# Agent Team 任务中途工具权限异常冻结：完整调查报告

**调查对象：** dsh-agent-team-presets 插件（v0.1.6）
**缺陷等级：** P1（阻断工作流）＋ P2（权限提升）
**调查方式：** 复现优先，定位根因，最小修复，独立审查
**报告性质：** 自包含。全部结论、证据与数据均在本文件内，不依赖任何外部文档。

---

## 摘要

用户报告：在选中 `builtin-standard` Team 的会话中，工具先正常工作，随后在同一个任务中途突然全部不可用，模型只能做自然语言回复，无法继续工具驱动的工作。报错文案指向「Team 无法安全恢复到已运行的任务中」。

调查结论是：**这不是热重载导致的，也不是安全隔离本身的错误，而是一处输入分类缺陷**。插件在「Agent 忙碌且本实例没有已应用策略记录」时，只检查是否存在 Team 选中项，就一律对整台 Agent 施加全量工具拒绝。这个条件把两类语义完全相反的输入混为一谈：一类是历史确实不可知、必须保守隔离；另一类是会话本来就以「无 Team」状态运行、用户中途选了一个 Team，此时没有任何既有策略被放宽，冻结纯属误伤。后者不需要任何热重载就能触发，与用户描述完全吻合。

调查还发现两个报告未提及的缺陷：一是任务中途取消选择再重载插件，会让原本的严格策略整个消失，属于任务中途权限提升；二是修复过程中一度引入的 fail-open（守卫被跳过后回落默认全量工具），被独立审查捕获并已修复。

修复遵循「最小必要、不放宽安全边界」原则：没有删除隔离机制，没有让守卫无条件放行，没有移除工具白名单或呈现方式逻辑。全部 638 项测试通过，另有 1 项在基线中即被跳过。

## 一、故障现象与安全前提

报告描述的可观察事实是：同一个任务内，早期工具调用成功，后期连只读工具和消息工具都失败，但模型仍能输出自然语言。这个形态本身已经指向结论——自然语言回复不需要经过工具守卫，而工具调用全部被拒，说明拒绝发生在工具层的统一入口，而不是某个具体工具自己报错。

调查前先确立必须被保留的安全不变量，这些是判断「哪些限制是应有的、哪些是缺陷」的基准：

1. 运行中的任务必须保留为该任务冻结下来的权限。
2. 新选中或被编辑的 Team 不得在任务中途悄悄扩大权限。
3. 插件重载绝不能导致默认放开权限。
4. 无法验证的历史策略可以要求保守隔离。
5. 隔离的作用范围必须精确，不能波及无关会话。
6. 到达安全边界后，合法会话应能可靠恢复。

这些不变量决定了修复的方向：任何「让报错消失」的做法，只要违反上述任一条，就是错误的修复。特别是「删除隔离」和「让守卫放行」被明确排除在外。

## 二、调查方法

调查在插件仓库的测试环境中进行，使用仓库自带的组合测试装置：真实的依赖注入容器、真实的 Agent 执行循环、真实的 Team 服务契约替身，以及可控制节奏的模型适配器（可让 Agent 停留在运行状态以观察冻结行为）。不接触用户真实工作区，不重启正在运行的宿主服务，不修改任何已安装的实例副本。

对报告中的十个候选场景逐项建立独立用例，每个用例都遵循同一流程：先确认基线工具可用，引入单一状态变化，再次调用工具并记录精确报错，然后让 Agent 与队员真正回到空闲边界，观察是否能自动恢复。凡是观察到的行为像缺陷，用例先如实断言当前实际行为并在注释中标出，保证用例全绿而缺陷可见；修复后再把断言改为期望行为。

共建立 31 个用例，覆盖重挂载、中途选中、Team 切换、冷启动、Team 被删除、非法白名单、队员卡死、并发写入等场景，另含修复后新增的提权、恢复集精确性、失败回滚、呈现方式证据等用例。

## 三、复现结果

| 场景 | 结论 | 关键观察 |
|---|---|---|
| 任务中途重挂载插件 | 复现 | 该 Agent 全部工具被拒，边界后自动恢复 |
| 连续多次重挂载同一任务 | 复现 | 仍冻结，但无遗留守卫，边界恢复 |
| 无 Team 会话中途选中 Team | **复现（主根因）** | 没有任何既有策略可保护，却全量冻结，角色设定为空 |
| 冻结中再次取消选择 | 复现 | 文案仍点名已不存在的 Team，推荐动作无效 |
| 队员运行而队长空闲 | 复现 | 同样冻结，队员结算后才恢复 |
| Team A 切换为 Team B | **未复现** | A 保持生效，工具可用，边界后采纳 B |
| 冷启动或空闲重挂载 | 未复现 | 正常应用并恢复，含成员工具 |
| 选中的 Team 被删除 | 复现（持久） | 持续拒绝，重挂载后仍拒，清空选择或恢复 Team 才恢复 |
| 运行中 Team 被删除 | 复现 | 运行中不变，边界后转为全拒 |
| 白名单命名不可达能力 | 复现 | 文案可操作，修正后自动恢复 |
| 运行中白名单变非法 | 未复现 | 原策略保持 |
| 队员永不结算 | 复现（无界） | 两次边界后仍冻结，且中断工具也被拒 |
| 连续并发写入并取消 | **未复现** | 无遗留守卫、无提前放权 |
| 中途取消选择后重载 | **复现（权限提升）** | 严格策略整个消失，被排除的工具全部放行 |
| 隔离作用范围 | 通过 | 严格按 Agent 隔离；子 Agent 由自身守卫拒绝 |
| 从未选过 Team 的会话重载 | 对照通过 | 保持部署默认，行为正确 |

两点必须如实标注。第一，全部结论来自进程内组合测试，未使用真实模型与真实宿主进程。第二，某个特定工具呈现方式（PTC）下的阴性结论来自源码路径核实而非端到端运行，因为测试环境未装载该运行时；这一限制直接影响了后续的证据设计。

值得单独指出：Team A 切换为 Team B 与「无 Team 切换为 Team A」在代码上走的是同一个「忙碌且无新应用」的形状，但前者不冻结、后者冻结。这种不对称本身就说明分类依据用错了——两者真正的差别不在「是否忙碌」，而在「是否已有生效策略」和「历史是否可证」。

## 四、根因分析

### 4.1 主根因：把两类相反输入当成一类

消息冻结的发生点，是应用流程里的一个提前返回分支。它在 Agent 忙碌时执行以下判断：如果本实例没有该会话的已应用策略记录，且该会话存在 Team 选中项，就对整台 Agent 施加全量工具拒绝，然后返回。

这个条件缺了一个维度。它检验的是「忙碌 + 无记录 + 有选中」，而没有检验**这个任务究竟是在什么策略下开始的**。于是两种输入被同等对待：

- **历史不可知。** 插件在任务中途被挂载或重载，旧实例为这个任务冻结的权限已经丢失，当前设置里的定义不能代表任务开始时的定义。此时保守隔离是正确的，因为放行可能让运行中的任务获得它原本被排除的能力。
- **历史可证为「无 Team」。** 会话从头就以部署默认策略运行，用户在任务中途选了一个 Team。此时不存在任何被放宽的既有策略，冻结没有保护任何东西，只是把本来合法可用的工具全部拿走。

用户报告的故障正是第二种。因为触发条件与热重载无关，所以「任务进行到一半突然全灭」完全可以在一次普通操作中发生。

### 4.2 次要缺陷：隔离没有留出恢复通道

隔离的实现是对该 Agent 注册一个单调拒绝的守卫，其判定函数无条件返回同一段拒绝文案。工具守卫的语义是「只能否决、不能允许」，因此它对任何工具名都生效，包括插件自己注册的预设读取与编辑工具，以及 Team 内部的协作工具。

这造成了一个死循环：拒论文案让用户「在会话的 Team 控件里换一个 Team 或选无 Team」，但模型既无法调用读取预设的工具来诊断发生了什么，也无法调用消息工具告知队员或用户。用户看到的是「连只读工具都不能用了」，而推荐的补救动作在会话内无法执行。

### 4.3 权限提升：只看选中项，不看日志证据

同一处分类逻辑还漏掉了相反方向的情形。判断「是否隔离」只依据当前是否存在 Team 选中项，而没有参考会话自身的历史。

于是出现这样一条路径：某个 Team 已在任务中生效，用户在任务中途取消选择，此时旧策略仍按冻结规则继续生效；随后插件被重载，新实例看到「无选中项 + 忙碌」，不进入隔离分支，会话直接回落到部署默认工具面。原 Team 排除的工具与协作工具全部变得可用，角色设定也被清空。

这是任务中途的权限扩大，直接违反「运行中任务保留其冻结权限」这条不变量。它比原先报告的冻结问题更严重，因为冻结只是拒绝服务，而这是放权。

### 4.4 修复过程中一度引入的 fail-open

第一轮修复为了在「回滚也失败」时保留更精确的诊断文案，引入了一个标记集合，并在决定是否隔离时把它作为条件之一。但另一处清理分支漏了同时清除该标记。

结果是一条三段式路径：更新失败且回滚也失败（进入隔离并打上标记）→ 用户选择「无 Team」（守卫被撤下，但标记残留）→ 用户再选择一个非法 Team（此时决定是否隔离的逻辑因为标记仍在而跳过隔离）。最终这台 Agent 既没有守卫、也没有策略，直接以部署默认全量工具运行。

这个缺陷由独立审查在代码状态机审计中发现，并在修复前被独立复现确认：那台 Agent 上的两个探针工具都被放行。修复后同一条路径上的两个探针都被正确拒绝，且拒绝文案指向真正的原因。修复采用双重加固：在清理分支显式清除标记，同时在决定是否隔离处增加「只要守卫不在位就一律补装隔离」的兜底，宁可覆盖更精确的文案，也绝不跳过守卫。

## 五、证据设计上的一个关键取舍

修复需要区分「历史不可知」与「可证为无 Team」。理想方案是持久化每个任务冻结的策略快照，但那是独立的大改动，涉及原子提交顺序、身份绑定、版本与损坏处理。本次采用两条更轻的证据。

**阳性标记。** 每个会话自身的请求头事件里，记录了该次请求实际发给模型的工具名。插件注册的成员工具名在整个部署中只有本插件的一条注册路径，因此它的存在可以证明「这个会话确实曾在 Team 策略下运行」。这条证据只用于阳性判断：存在即证明曾在 Team 下运行；缺失则什么也证明不了。

缺失为什么不能作为阴性证明，调查中核实了两个确定的反例。其一，某些工具呈现方式下，模型实际看到的工具表会被折叠成单一入口工具，此时成员工具虽已注册却不会出现在请求头里。其二，宿主是先进入运行状态、再异步组装提示、再准备请求，最后才写请求头；因此「正在运行但还没有新请求头」是可能状态，此时最新的请求头可能仍属于上一个任务。

这两个反例直接否定了我最初设想的「有标记即为历史不可知，无标记即为可证无 Team」的二分法。必须承认：缺失只能视为未知。这一点在实现中被写进判定函数的注释，并由测试锁定。

**可信基线。** 对第二种输入，改为要求本实例亲自见证过一个可信边界：该会话在非忙碌状态下，没有选中项、没有已应用策略、没有隔离、也没有排队中的首次应用。只有在这种情况下，才认为「这个任务确实是无 Team 起步」，中途选择只需静默延后到边界，不必冻结。这个基线在任何一次应用、安装隔离、出现排队应用或会话销毁时立即失效，避免过期证据被误用。

## 六、修复内容

修复共改动三个源文件，净增 199 行、删除 8 行。

**恢复通道。** 为队长精确列出十个豁免名：预设读取、预设编辑、发送消息、列出队员、等待队员、中断队员，以及四项任务板操作。这是一份字面量清单，不从既有的预设工具组或 Team 工具组派生——那两个组里含有创建成员或创建队员的入口，不能顺带放开；也不使用前缀匹配。子 Agent 不享受任何豁免，因为队员没有会话控件、也没有预设权限，对它放行等于允许在没有策略的情况下行动。豁免的语义是「这个守卫不否决」，不是强制允许，因此其它守卫、宿主权限与审批流程仍然照常生效。

**分类重写。** 忙碌分支改为按证据分档：该会话已有生效策略时，运行中的任务原样保留；没有策略但存在选中项时，继续保守隔离；没有策略也没有选中项，但日志证明曾在 Team 下运行时，立即隔离（这是堵住权限提升的那一支，它使隔离不再依赖当前是否还有选中项）；没有策略、没有选中项、没有标记，但本实例见证过可信无 Team 边界时，静默延后到边界；其余情形维持不隔离。

最后一档是一个明确的取舍。把「未知且无选中项」也收紧为隔离，会冻住「从未选过 Team、插件恰好在任务中途重载」的用户——而这正是本次报告的故障形态。用一个更宽的拒绝服务去补一个更窄的放权窗口，不成立。

**失败回滚改为不放开。** 当更新失败、回滚也失败时，立即释放半安装的部分、清除应用记录、定义与角色绑定，并马上安装隔离，文案中给出上一个 Team 的身份、原始错误与恢复指引。不能依赖后续的拒绝分支来兜底，因为被取代的任务会直接返回，而某些错误发生在记录写入之后，会让后续逻辑误以为已有有效策略。

**诊断标记的生命周期闭环。** 在切到「无 Team」的分支中显式清除失败标记；在决定是否隔离处增加「守卫不在位则一律补装」的兜底。

修复前对照的做法是：把源码改动临时移出，在原始版本上运行同一套新增用例，确认失败点确实落在修复项上，然后恢复。这证明用例不是「怎么写都通过」的空测试。

既有用例全部未改动且继续通过，包括重挂载冻结后边界恢复、权限矩阵、预设工具、安全回归等，说明 Team 的创建、切换、中断与恢复路径未受影响。跳过的 1 项在调查开始前的基线中即已跳过，不计入通过。

需要如实说明一点：新增用例中有 5 条关于工具呈现方式与残余窗口的用例在修复前也通过。它们断言的是「阴性证据不可作为放行依据」在下游的表现，属于保护性用例而非修复点，因此修复前同样通过。判定函数本身的语义由注释与恢复集精确性用例锁定，不能用这几条的通过来夸大修复覆盖。

## 八、安全评估

五条不变量逐条复核后均成立。

运行中任务保留冻结权限：忙碌且有生效策略时直接返回，不做任何替换。新选或编辑的 Team 不在中途扩权：运行期间绝不安装新定义，只排队到边界后串行应用。重载不默认放开：日志证明曾在 Team 下运行即强制隔离。不可验证的历史策略保守隔离：拒绝即隔离，回滚失败也隔离。作用域精确：守卫注册在单个 Agent 的作用域上，子 Agent 无豁免，另一个会话不受影响，后两点均有独立用例。

对两个被豁免的非能力工具做了专项核查。预设编辑工具只接受描述与提示词类字段，不接受工具策略字段，并且受修订号、用户指令与审批三重约束，无法用于自我扩权。发送消息工具确有副作用：它可以唤醒处于非活动状态的队员，使该会话持续处于忙碌，从而推迟任务边界到达；但它不能派生成员、不能改变自身权限。这是如实披露的权衡，不是「整个 Team 停止活动」的保证。

所有创建入口、通用代码执行、委派与普通能力工具、以及未知工具名，在隔离期间仍全部拒绝，并有测试以探针方式证明其执行体从未被调用。

## 九、未解决的风险与边界

**残余窗口（已知，未修复）。** 若某个 Team 在空闲时被应用，随后任务被唤醒，宿主尚未构建新的请求头时用户取消选择，接着插件被重载，则最新的请求头仍是上一个「无 Team」任务的阴性结果，该会话被归为未知而不隔离。触发它需要同时满足任务中途重载、并发取消选择、且恰好卡在请求头构建之前，窗口极窄。修复它会伤及正常用户，已写成显式用例并在实现中标注为已知窗口、不得作为放行依据。

**跨重载无缝续跑未实现。** 需要在新任务身份下持久化完整冻结定义与恢复所需信息，建立写入、应用与任务边界的原子顺序，并对缺失、版本不支持、损坏、身份不匹配一律隔离。这是独立变更，不在本次范围。

**插件卸载到新实例接管的窗口未覆盖。** 卸载会释放守卫，这段间隙的能力状态需要宿主生命周期层面的交接契约，本次不声称已覆盖。

**队员永不结算时的无界冻结。** 该会话仍会保持冻结，但现在中断工具可用，用户具备自救手段；宿主侧的队员结算超时不在本次范围。

**其它未验证项。** 特定工具呈现方式的端到端行为未运行（测试环境无该运行时）；多租户并发重载下的内存压力、以及超大日志下的历史扫描延迟未做压测（实际实现倒序查找，通常首条即命中）。

## 十、结论与建议

用户报告的冻结可稳定复现，根因是隔离触发条件缺少「任务起始策略」这一维度，把「历史不可知」与「可证无 Team」混为一谈；它与热重载无关，但热重载是最容易暴露它的一条路径。同一处逻辑还遗漏了相反方向的权限提升，以及隔离期间没有保留任何恢复通道。

修复没有削弱安全边界：隔离仍然存在，守卫仍然是单调拒绝，白名单与呈现方式逻辑未被触碰；改动集中在证据分类、恢复通道与失败回滚三个方面，并配有可反向验证的回归测试。

后续若产品需要「插件重载后无缝继续原任务」，应作为独立变更引入持久化的冻结策略快照，并明确其崩溃恢复与版本兼容语义；在此之前，无法验证历史的任务继续隔离到边界，是当前可接受的保守行为。
